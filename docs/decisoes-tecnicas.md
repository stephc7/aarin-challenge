# Decisões técnicas relevantes (e por quê)

Durante o mapeamento da automação, o ambiente real revelou comportamentos que não estavam nos requisitos e que moldaram as decisões abaixo. Ver [README](../README.md) para visão geral do projeto.

- **Seleção de variação é dinâmica, não fixa.** A PDP de um produto variável (`Ingrid Running Jacket`) publica todas as combinações de Tamanho/Cor em `data-product_variations`, e **algumas combinações existem na UI mas estão fora de estoque** (ex.: `M + Red`). Fixar uma combinação no código quebraria o teste sempre que o estoque mudasse. `ProductPage.selectFirstAvailableVariation()` lê esse JSON e seleciona dinamicamente a primeira combinação `is_in_stock: true`.
- **"Ver opções" fica em um overlay só revelado por `:hover`, com bounding box 0×0 por padrão.** Simular hover real antes do clique (`.hover()` + `.click()`) é instável nesse tema (o overlay pode fechar entre as duas ações). A solução foi disparar o clique nativo via `element.click()` (`locator.evaluate`), que aciona a mesma navegação do link sem depender de estado visual.
- **Atualizar quantidade no carrinho substitui a linha inteira via AJAX.** Clicar em "Update Cart" pode disparar uma verificação de estabilidade do Playwright contra um botão que já foi substituído no DOM pela resposta AJAX, fazendo `.click()` "pendurar" até o timeout mesmo com a ação já efetivada no servidor. A verificação real de sucesso é feita no valor final do subtotal (`expect(...).toHaveText(...)`, que faz polling), não no clique em si.
- **Dados de cliente são únicos por execução.** O ambiente é uma loja WooCommerce pública e compartilhada, um "Finalizar Compra" bem-sucedido cria um **pedido real**. `buildTestCustomer()` gera nome/e-mail com timestamp para não colidir com dados de outras execuções e para deixar claro, para quem administra o ambiente, que aquele pedido veio de automação.
- **Prefixo de e-mail padronizado para todo dado gerado pela automação.** `buildTestCustomer()` (pedidos) e `buildTestAccount()` (contas de cliente) usam o mesmo prefixo `qa.automation+`, seguido de um marcador de tipo e do timestamp (`qa.automation+order.<timestamp>@example.com` / `qa.automation+account.<timestamp>@example.com`). Isso permite ao time responsável pelo ambiente encontrar e limpar **todo** dado de teste buscando por `qa.automation+`, ou isolar por tipo (`order.` vs. `account.`) quando necessário.
- **Adicionar ao carrinho pela vitrine abre um modal, não o banner inline da PDP.** Na PDP, a confirmação é um banner `.woocommerce-message`; na vitrine (home/listagem), é um modal `.popup-cart`. São fluxos de confirmação diferentes no mesmo tema, `ProductListPage.addSimpleProductToCart()` aguarda o modal antes de navegar para outra página. Navegar cedo demais fazia o carrinho aparecer vazio mesmo com o item já adicionado no servidor.
- **Nem todo item de carrinho tem quantidade editável.** Produtos marcados como "vendido individualmente" no WooCommerce mostram a quantidade como texto fixo (sem `input.qty`) em vez do stepper editável usado no fluxo obrigatório. `CartPage` expõe `getItemQuantityInput()` (editável) e `getItemQuantityCell()` (texto fixo) como métodos separados em vez de um único método que "adivinha" o formato.
- **Remover item do carrinho é uma navegação real, não AJAX puro.** O link "×" aponta para uma URL com nonce (`/carrinho/?remove_item=...&_wpnonce=...`); o servidor processa a remoção e redireciona de volta. Mesma característica de bounding box 0×0 dos outros controles do tema, então usa o mesmo clique nativo via `evaluate()`.
- **Os três métodos de pagamento do ambiente (COD, bacs, cheque) são "manuais", nenhum depende de gateway externo (cartão, PayPal etc.), verificado direto na tela de checkout.** Todos finalizam o pedido de ponta a ponta sem exigir dados bancários reais, mudando apenas o rótulo de "Método de pagamento" na confirmação. O fluxo obrigatório usa COD por ser o primeiro da lista, não por ser o único que funciona, bacs e cheque são cobertos à parte em `payment-methods.spec.ts`.
- **O formulário de cadastro tem proteção anti-bot que descarta a submissão em silêncio.** Preencher `#reg_email`/`#reg_password` com `fill()` (que define o valor direto, sem eventos de teclado) faz o clique em "Register" não fazer nada, sem erro, sem redirecionamento, sem log de rede. Trocar para `locator.pressSequentially()` (digitação simulada de verdade) resolve. `AccountPage` usa esse método tanto no cadastro quanto no login, por consistência.
- **As mensagens de erro de login/cadastro revelam se um e-mail existe na base** (“Endereço de e-mail desconhecido” vs. “A senha... está incorreta” vs. “Uma conta já está registrada com seu endereço de e-mail”). Do ponto de vista de UX isso é conveniente, mas é uma enumeração de contas, um risco de segurança que registrei como achado de qualidade, não como bug bloqueante (fora do escopo funcional deste desafio).
- **A caixa de busca do header é revelada por um ícone que abre um modal**, e o tema duplica o formulário de busca várias vezes no DOM (variações ocultas para outros breakpoints). `SearchPage.search()` clica no ícone via `:visible` (não pelo primeiro elemento do DOM, que pode ser uma cópia oculta) antes de preencher o campo, mesma classe de problema já vista no botão "Ver opções" da vitrine, mas com uma causa diferente (modal fechado por padrão, não CSS `:hover`).
- **Criar conta durante o checkout ("Criar uma conta?") não tem a mesma proteção anti-bot do cadastro em /minha-conta/.** `fill()` funciona normalmente no campo `#account_password` do checkout, a proteção parece ser específica do formulário de registro standalone, não do fluxo de conta embutido no checkout.
- **Quantidade inválida na PDP falha em silêncio.** Definir a quantidade como 0 ou negativa e clicar em "Comprar" não dispara nenhuma chamada de rede, o clique é ignorado pelo JS do WooCommerce sem nenhuma mensagem de erro visível ao usuário. Funcionalmente correto (nada é adicionado), mas é um ponto de UX que vale nota: o usuário não recebe feedback do porquê nada aconteceu.
- **Bug encontrado (BUG-001, ver [README](../README.md#bugs-encontrados)):** ao definir a quantidade do carrinho como um valor negativo e clicar em "Update Cart", o servidor corretamente rejeita o valor e mantém o total original, mas o campo de quantidade na tela continua mostrando o valor negativo digitado em vez de reverter para o valor real (1), até a página ser recarregada manualmente. É uma inconsistência entre o que a UI exibe e o que o servidor persistiu, não uma falha de cálculo.
- **Adicionar dois produtos em sequência pela vitrine exige fechar o modal entre uma adição e outra.** O modal de confirmação (`.popup-cart`) é o mesmo elemento reaproveitado a cada clique em "Comprar" — chamar `addSimpleProductToCart()` duas vezes seguidas fazia o segundo `waitFor({ state: 'visible' })` resolver instantaneamente (o modal já estava visível pela primeira adição), sem esperar de fato a segunda chamada AJAX terminar, e o carrinho às vezes só mostrava o primeiro item. A correção fecha o modal ao final de cada chamada, garantindo que a próxima espere uma transição real de oculto→visível.
- **Clique duplo em "Finalizar Compra" é bloqueado por um overlay (`blockUI`)** que aparece assim que a primeira submissão começa, impedindo cliques adicionais no botão. O teste dispara dois `.click()` nativos no mesmo `evaluate()` (não duas chamadas `.click()` do Playwright, que já seriam serializadas pela checagem de actionability e não reproduziriam um clique duplo real) e confirma que apenas uma navegação para a confirmação do pedido acontece.
- **O dropdown de ordenação (`/produtos/`) envia o formulário via JS assim que o valor muda**, recarregando a página inteira (não é AJAX). Encadear `selectOption()` com `page.waitForLoadState('domcontentloaded')` falhava com "Execution context was destroyed": como a página atual já estava nesse estado, a promise resolvia antes mesmo da navegação começar. A correção usa `page.waitForURL(/orderby=/)` em paralelo com o `selectOption()`, que só resolve quando a URL realmente muda.
- **A seção "Produtos Sugeridos" da home sorteia posições a cada carregamento.** Um mesmo produto pode aparecer, numa visita, no primeiro slot visível do carrossel, e noutra, só em cópias ocultas (usadas para outros breakpoints). Isso quebrava a checagem do preço promocional quando calhava de pegar uma cópia oculta: `innerText()` retorna string vazia para elementos ocultos. A correção usa `textContent()` (que não depende de visibilidade/layout) para ler dados que não exigem clique, reservando `:visible` apenas para elementos que realmente serão clicados.
- **Nem todo produto tem produtos relacionados configurados.** "Ingrid Running Jacket" não tem a seção "Related products"; o teste de CT-028 usa outro produto (`[66665692] Produto Lgc2`) que tem. Ao contrário dos botões "Comprar"/"Ver opções", o link da imagem do produto relacionado é um `<a>` simples sem overlay de hover, então um clique comum do Playwright funciona sem precisar do clique nativo via `evaluate()`.
- **Enviar uma avaliação sem nota/nome/e-mail é bloqueado em silêncio**, mesmo padrão já visto na quantidade inválida da PDP (CT-025): o formulário tem `novalidate` (desativando a validação nativa do navegador) e o JS de validação intercepta o submit sem exibir nenhuma mensagem de erro nem disparar o POST para `wp-comments-post.php`. Funcionalmente correto (nada é publicado), mas mais um ponto de UX sem feedback ao usuário.
- **O menu principal do header também é duplicado no DOM** (cópia oculta para mobile), a mesma classe de problema já vista em "Ver opções" e na busca, aqui a solução é mais simples: como o link do menu não precisa de clique nativo via `evaluate()` (não fica atrás de um overlay de `:hover`), basta filtrar por `a:visible` para pegar a cópia certa antes do clique comum do Playwright.
- **Adicionar à wishlist tem o mesmo bug de sincronismo já visto no carrinho, mas exige um sinal de espera diferente.** Sem aguardar a confirmação do AJAX, `/lista-de-desejos/` aparecia vazia mesmo com o clique já disparado. A correção óbvia de, esperar a mensagem "Produto adicionado!" ficar `visible` —\\, falhava sempre: esse elemento fica escondido por CSS até o usuário passar o mouse sobre o ícone (mesmo padrão de overlay do tema), mas já está no DOM assim que o AJAX termina. Trocar para `waitFor({ state: 'attached' })` resolve, o sinal certo é existir no DOM, não estar visualmente visível.
- **"Remember me" é verificado pelo cookie de sessão, não pela UI.** Não há nenhuma indicação visual de que a sessão vai durar mais, a única forma observável é inspecionar `wordpress_logged_in_*`: sem a opção marcada é um cookie de sessão (`expires: -1`); marcado, ganha uma data real ~14 dias no futuro (padrão do WordPress).
- **O comparador de produtos (YITH Compare) abre a tabela num iframe dentro de um colorbox (lightbox), com `name` dinâmico** (timestamp), então o iframe é localizado pelo `src` (estável) via `frameLocator()`. Mesmo bug de sincronismo do carrinho/wishlist aqui também: adicionar um segundo produto sem esperar a tabela do primeiro carregar fazia a segunda coluna não aparecer. **Achado de qualidade:** a tabela de comparação neste ambiente não exibe nome, imagem nem preço dos produtos, só os botões "Remover" por coluna. O teste verifica a estrutura (uma coluna por produto, remover tira a coluna certa) em vez do conteúdo, que a aplicação não preenche.
- **Não existe listagem pública de cupons ativos**, então o cupom válido usado como contraparte positiva do CT-016 não veio de nenhum material do desafio, foi encontrado testando um pequeno lote de códigos plausíveis (nome da loja + percentuais comuns de desconto) direto no campo de cupom do carrinho. `EBAC10` e `DESCONTO10` são válidos, ambos aplicando 10% de desconto, o teste usa `EBAC10`.
- **Falha rápida quando uma suposição sobre o catálogo compartilhado deixa de ser verdadeira.** Como não temos como impedir que o catálogo mude (é uma loja compartilhada, ver [Limitações conhecidas](../README.md#limitações-conhecidas)), `ProductListPage.addSimpleProductToCart()`/`addToCompare()` verificam que o produto ainda existe antes de tentar interagir com ele, lançando um erro específico em vez de deixar o Playwright estourar um timeout genérico 30s depois num clique num elemento que nunca vai aparecer. Mesmo raciocínio para a asserção de "vendido individualmente" em `simple-product.spec.ts`, que usa uma mensagem customizada do `expect()` em vez do diff padrão.
- **O botão "Comprar" de um produto variável não usa o atributo HTML `disabled` enquanto nenhuma variação é selecionada, só a classe `disabled` (com `pointer-events` bloqueado via CSS).** Um `.click()` comum do Playwright ficaria esperando o elemento se tornar "clicável" (accionability check) até estourar o timeout, já que ele nunca considera um elemento com `pointer-events: none` como clicável. `ProductPage.attemptAddToCartWithoutSelection()` usa o mesmo clique nativo via `evaluate()` já usado nos outros botões bloqueados por CSS do tema, confirmando que o clique realmente não adiciona nada ao carrinho (CT-004).
- **O teste de preço promocional (CT-024) não depende de um produto específico.** A asserção (desconto exibido bate com o percentual do selo) não se importa com *qual* produto está em promoção, só que exista algum. `ProductListPage.getFirstOnSaleCard()` descobre dinamicamente o primeiro item com selo `.onsale` na vitrine, eliminando o acoplamento ao `SIMPLE_PRODUCT` continuar em promoção especificamente (diferente da suposição de "vendido individualmente", que é uma característica do produto em si e não tem como ser genérica).
